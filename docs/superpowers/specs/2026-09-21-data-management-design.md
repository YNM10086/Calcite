## 1. 目标与范围

### 要做什么

把现在那个**只能加、不能改**的「导入轨迹」按钮，升级成一个完整的**「数据管理」视图**：

| 操作 | 作用于 | 说明 |
|---|---|---|
| **添加数据** | 新增一条 | 现有的上传功能**整个搬进这个视图** |
| **替换** | 表格里的某一条 | 用新文件覆盖它的数据 |
| **改名** | 表格里的某一条 | 改显示名 |
| **删除** | 表格里的某一条 | 删掉它（连带它的点） |

### 为什么要做

设计里有多处注释写着「**因为目前没有"删除轨迹 / 重新导入覆盖同名轨迹"功能，所以缓存永不失效**」——
`StayPointCache` 和 `SimilarityCache` 的 javadoc 都明确写着「将来加了这些功能，**必须调用 `invalidate` 清理**」。

这个功能就是**来兑现那笔账的**。

### 成功标准

1. 能在一个视图里完成 添加 / 替换 / 改名 / 删除
2. **删一条轨迹后，四个分析功能的结果立刻反映这个变化**（不是缓存的旧结果）
3. **删错了能找回来**（回收站目录里有完整的导出）
4. 现有的 121 + 123 + 10 个脚本**保持全绿**
5. 前端面板**不再继续堆东西**（四个操作收进独立视图）

## 2. 后端 API

### 2.1 端点

```
POST   /api/tracks/import          现有，扩展：加 mode 与 replaceTrackId
PATCH  /api/tracks/{id}            新增：改名
DELETE /api/tracks/{id}            新增：删除
```

### 2.2 `POST /api/tracks/import` 的扩展

现有行为（**完全不变**）：上传文件 → 算内容 SHA256 → `externalId` 已存在就跳过（幂等）。

新增的**同名检测**：

```
① 上传文件
② 算内容 SHA256（现有逻辑）
③ external_id 已存在        → 跳过（幂等）✓ 行为不变
④ external_id 是新的、
   但 name 已存在            → 返回 409 Conflict
                              + { existingTrackId, existingName,
                                  existingPointCount, newPointCount }
⑤ 用户在界面上选：
     "替换" → 重新提交，带 mode=replace & replaceTrackId=<existingTrackId>
     "新增" → 重新提交，带 mode=append（默认）
```

**⚠️ 还有第二个冲突要处理（自查时发现的边界）**：

替换时，新文件的 `external_id`（= 内容 SHA256）**可能已经属于另一条轨迹**：

```
先导入「资料一」→ 它的 external_id = A
再拿【同一个文件】去"替换"「资料二」
  → 新的 external_id 也是 A，但 A 已经是「资料一」的
  → 撞唯一约束 → 500
```

**正确行为**：这不是错误，是「**这份内容已经在库里了**」——
应该**再返回一次 409**，说清楚"这个文件的内容已经是『资料一』了，你是想替换『资料二』还是算了？"。

**不要让它变成 500** —— 用户会以为系统坏了，而实际上是他自己传了一份已经在库里的文件。

**为什么用 409 + 让用户决定，而不是系统按名字自动替换**：

- 「同名」本质上是个**意图问题** —— 同一个名字，你可能想覆盖，也可能就是想留个对比版本
- **自动替换是不可逆的**（用户的数据被静默覆盖）；让用户点一下，最坏也只是多点一次
- 这样就不需要定义「同名」的边界（区分大小写？带不带扩展名？跨来源算不算？）—— **这些问题一起消失了**

### 2.3 替换保持 `trackId` 不变

替换是**原地更新**（geom、点数、时长、external_id、时间范围），**不删不插**。

> 界面上用户选"替换"时，**不需要重新选文件** —— 浏览器里 `File` 对象还在内存里，
> 直接用同一个对象再提交一次即可（不会真的重传一遍磁盘读取）。

好处：
- 前端选中的轨迹不会失效
- 缓存失效范围更小（但还是必须清，见第 3 节）

### 2.4 `PATCH /api/tracks/{id}`

```json
{ "name": "新的名字" }
```

校验：非空、去首尾空格、长度 ≤ 200。

**不校验唯一性** —— 这是 2.2 那个决定的必然结果（允许重名，因为"要不要覆盖"由用户当场决定）。

### 2.5 `DELETE /api/tracks/{id}`

**流程（顺序很重要）**：

```
① 查这条轨迹存不存在 → 不存在 404
② 【先导出到回收站】（见第 4 节）—— 失败就中止，不删
③ 删 track（它的点由 FK ON DELETE CASCADE 自动删）
④ 清缓存
```

## 3. ⭐ 缓存失效（这个功能的核心风险）

### 3.1 要清什么

| 操作 | 清什么 | 为什么 |
|---|---|---|
| **删除** X | `StayPointCache.invalidate(X)`<br>`SimilarityCache.invalidateAll()` | X 自己的缓存没用了；**而且别的主线的相似度结果里可能把 X 算进去了** → 必须**全清** |
| **替换** X | 同上 | 数据变了 |
| **改名** X | **`SimilarityCache.invalidateAll()`** | ⚠️ 见下 |

### 3.2 ⚠️ 改名也必须清相似度缓存（最容易漏的一点）

看起来"只是改个显示名、数据一点没变"，**不该影响相似度**。

**但 `SimilarityMatch` 里带了 `name`** —— 所以别的主线的匹配列表里会显示**旧名字**。

不清的后果很具体：把「资料一」改名成「第一次跑步」，然后点另一条主线的相似度，
列表里还是写着「资料一」—— **改了个寂寞**。

### 3.3 为什么宁可全清（`invalidateAll`）而不是精准清

精准清需要：遍历所有主线的相似度结果 → 看谁包含被删的那条 → 只清那些。

**复杂度远大于收益**，而且**漏一个就是"界面显示一条已经不存在的轨迹"**。

全清的代价只是"下次点相似度要等 2 秒"。**宁可全清，不要漏清。**

### 3.4 这两个类已经写好了

```java
StayPointCache.invalidate(Long trackId)     // 已存在
SimilarityCache.invalidate(Long trackId)    // 已存在
SimilarityCache.invalidateAll()             // 已存在
```

**本阶段要做的是"把它们接到调用点上"，不是从零补洞。**

## 4. ⭐ 删除的回收站（用户明确要求加的保险）

### 4.1 做什么

**删之前，先把那条轨迹完整导出**到：

```
D:\Calcite-note\backups\deleted\
    20260921-2015_资料一_456点.geojson
    20260921-2020_20081023025304_908点.geojson
```

导出内容：轨迹的元数据（name / source / external_id / 起止时间）+ **全部点**（经纬度 / 海拔 / 时间）。

### 4.2 ⚠️ 导出失败就不删（fail-safe）

```
导出成功 → 才执行删除
导出失败 → 返回 500，轨迹原样保留，并在响应里说清"导出失败，未删除"
```

**这一条是整个保险的灵魂**：如果是"尽力导出、失败也照删"，那这个保险就是假的 ——
用户以为有回收站，实际某次磁盘满了就静默没了。

### 4.3 为什么用 GeoJSON 而不是别的

- **标准格式**，QGIS / geojson.io / Python 都能直接打开
- 用户想手工看一眼被删的是哪条轨迹，**拖进 geojson.io 就能看**
- 文本格式，出问题了肉眼能读
- 附带的元数据放在 GeoJSON 的 `properties` 里，不丢信息

### 4.4 配置

```yaml
calcite:
  data:
    # 删除前的自动导出目录。**删之前先导出**，导出失败就不删。
    recycle-dir: D:\Calcite-note\backups\deleted
```

⚠️ **不复用 `calcite.import.allowed-roots`** —— 那个是**导入时的读白名单**（只允许从 GeoLife 目录读），
用途完全不同。混在一起会让两个安全策略互相牵制。

## 5. 前端：数据管理视图

### 5.1 结构

```
App.vue
  viewMode: 'stay' | 'hotspot' | 'density' | 'similar'   （分析视图，不变）
  panelView: 'analysis' | 'manage'                        （★ 新增）
      'analysis' → <TrackList> + 当前分析档的内容
      'manage'   → <DataManager>

TrackList.vue   把上传表单整个搬走；「导入轨迹」按钮改成「数据编辑」
DataManager.vue ★ 新建
  ├─ 顶部：[← 返回]   数据管理
  ├─ 「＋ 添加数据」区（原来的上传表单，原样搬过来）
  └─ 轨迹表格：一条一行，行尾 ✎ 🗑
```

**为什么是"整个面板切换"而不是"按钮下方展开"**（用户从三个方案里选的）：

1. **「一条轨迹一行 + 行尾操作」是最不容易点错的形态** —— 246 条里要删的是「资料一」还是「资料二」，
   表格形态一眼能确认
2. 折叠框里只能操作**当前选中**的那条，你得先回列表选、再展开、再删
3. **折叠框以后还会长** —— 用户最初的不满就是"继续堆在现在这个界面"

### 5.2 表格

**复用现有的筛选与分页**（`source` 筛选 + `limit` 下拉），不自造一套。

每行：`名称 · 来源 · 点数 · 长度 · 开始时间` + 行尾 `✎ 🗑`

### 5.3 改名

点 ✎ → 行内变成输入框（**行内编辑，不弹窗**）→ 回车保存 / Esc 取消。

**为什么不弹窗**：改名是个轻操作，弹窗太重；而且行内编辑能**看着那一行**改，不容易改错对象。

### 5.4 删除确认弹窗（用户选的最轻一档）

```
确定删除「资料一」？

会连带删除它的 456 个轨迹点。

💡 删除前会自动导出到
   D:\Calcite-note\backups\deleted\
   需要的话可以从那里找回来。
   数据库里删掉后，也可以重新导入原始文件。
```

> 最后那两行**很重要**：它把"不可恢复"从一句恐吓变成**一个真实的操作指引** ——
> 用户知道怎么办，就不会因为害怕而不敢用。

### 5.5 同名替换的交互

上传后如果后端返回 409：

```
已有同名轨迹「资料一」（456 个点）
你上传的这份有 623 个点

[ 替换它 ]   [ 新增为另一条 ]   [ 取消 ]
```

## 6. 连带影响（前端状态）

### 6.1 一条规则

> **数据一改，四个分析功能的结果全部失效。**

因为四个功能**全都基于全库数据**：

| 功能 | 为什么失效 | 怎么处理 |
|---|---|---|
| 轨迹列表 | 少了一条 / 名字变了 | 重拉 |
| 停留点 | 是"这条轨迹的点"算出来的 | 重新拉详情 |
| 热点 | 是**跨全部轨迹**聚出来的 | 后端缓存已清 → 重查 |
| 密度 | 是**全部轨迹的点**聚合出来的 | 重查 |
| 相似度 | 是**和全部轨迹比**出来的 | 后端缓存已清 → 重查 |

### 6.2 边界情况

| 情况 | 要做什么 |
|---|---|
| **删的是当前选中的轨迹** | 清空 `selectedId`、擦掉地球上的轨迹线、**自动切回「停留点」档**（不要停在一个已经没有数据的档位上） |
| **替换的是当前选中的** | 重新拉详情和点，地球重画 |
| **改名的是当前选中的** | 更新面板标题 + **重查相似度**（因为匹配列表里带名字） |
| **任何操作之后** | 四个分析档的本地状态**全部清空**，下次切过去时自动重查 |

## 9. 测试与验收

### 9.1 三层

| 层 | 测什么 | 需要数据库？ |
|---|---|---|
| **Java 单测** | `TrackExporter` 生成的 GeoJSON 结构；改名校验；同名检测的判定逻辑 | 部分（Exporter 写临时目录，不连库） |
| **Python 对拍** | 删/替换/改名的完整流程 + **缓存真的失效了** | ✅ |
| **浏览器验收** | 管理视图能进能出、表格、行内改名、删除确认、同名 409 流程 | ✅ |

### 9.2 ⭐⭐ 三条关键测试

**① 删除后相似度必须变（证明 `SimilarityCache` 真被清了）**

```
① 查 trackId=20 的相似度 → 记下 compared（实测 197）
② 删掉 track 39（它是第一名，91.1%）
③ 再查 trackId=20 的相似度
④ 断言：compared == 196，且 track 39 不再出现
```

> **为什么这条最重要**：它同时验证了「删除生效」和「缓存真的清了」。
> 如果缓存没清，第 ③ 步会返回**缓存的旧结果**，`compared` 还是 197 —— **立刻红**。

**② 改名后别的主线的匹配列表必须显示新名字（证明"改名也要清缓存"）**

```
① 查 trackId=20 的相似度，从 matches 里挑一条（比如 track 39）
② 把 track 39 改名成「测试改名-唯一标记」
③ 再查 trackId=20 的相似度
④ 断言：那条的 name == 「测试改名-唯一标记」
⑤ 改回原名（清理现场）
```

> 这条专测第 3.2 节那个**最容易漏的点** —— 光看"改名"两个字完全想不到要清缓存。

**③ 删除前必须真的落盘了回收站文件（证明 fail-safe 生效）**

```
① 记下回收站目录里现有的文件数
② 删掉某条轨迹
③ 断言：文件数 +1，且新文件名里带那条轨迹的名字和点数
④ 用 Python 读那个 GeoJSON，断言轨迹点数与删除前一致
```

### 9.3 浏览器验收

| 检查 | 判据 |
|---|---|
| 「数据编辑」按钮存在，点了进管理视图 | DOM |
| 管理视图有「← 返回」，点了回列表 | DOM |

| 四视口面板不溢出 | 1600×900 / 1600×600 / 1366×660 / 1280×720 |
| 控制台零报错 | |

### 9.4 ⚠️ 现有验收脚本要改成"数据自适应"

现有脚本大量假设"库里有 **246** 条轨迹"。**删一条就会打破它们。**

**修法同第三阶段那次**：全部改成**先从接口取当前总数**，不写死。

要改的脚本：`check-filter.py`（写死了总数）、`check-hotspots.py`、`verify-hotspot-api.py`、
`verify-similarity-api.py`（写死了 `compared == 197`）等。

> **⚠️ 特别注意**：`verify-similarity-api.py` 里有 `compared > 50`、`daysAway == 19` 这类期望。
> `daysAway` 是**特定两条轨迹的事实**（数据不变就不变）✓ 可以留；
> 但 `compared` 是**全库条数的函数** → 必须改成从接口取。

### 9.5 回归

现有 **后端 121 + node 123 + 浏览器/接口 10 个脚本**必须保持全绿。

## 10. 已知限制与明确不做的事

| 限制 | 说明 | 为什么不修 |
|---|---|---|
| **删除不可从界面恢复** | 有回收站文件，但**没有"一键还原"** | 还原要处理 trackId 冲突、external_id 冲突。**回收站是"能找回来"，不是"能点一下回来"** |
| **缓存全清而不是精准清** | 删/替换/改名都调 `invalidateAll()` | 精准清要遍历所有主线的结果看谁包含被删的。**漏一个就是"界面显示已删轨迹"** —— 宁可全清 |
| **不做"编辑轨迹的点"** | 不能裁剪、不能修单个坏点 | **另一个功能**（轨迹裁剪），要动 28.6 万个点 + 重算统计 + 做点编辑界面 |
| **不做批量选择/批量删** | 一次一条 | 表格形态已经为它留了位置，以后加"全选"很容易 |
| **替换必须同来源** | GPX 不能替换成 GeoLife | 来源变了语义就变了（一个是个人的、一个是数据集的） |
| **允许重名** | 改名不校验唯一性 | 2.2 那个决定的**必然结果** |
| **并发删除** | 两个人同时删同一条 → 后一个 404 | 个人项目，不做乐观锁 |
| **回收站会一直涨** | 没有自动清理 | 删一条才产生一个文件，而且**用户可能正需要它**。不做自动清理 |

## 11. 关键决策记录

### 11.1 为什么是"整个面板切换视图"而不是"按钮下方展开"

见 5.1。核心：**表格形态最不容易点错**，而且折叠框以后还会长。

### 11.2 为什么同名检测要返回 409 让用户决定，而不是自动替换

见 2.2。核心：**同名是意图问题，系统猜不准；自动替换不可逆**。

### 11.3 为什么替换要保持 `trackId` 不变

见 2.3。核心：前端选中的轨迹不会失效，缓存失效范围更小。

### 11.4 ⭐ 为什么改名也要清相似度缓存

见 3.2。核心：`SimilarityMatch` 里**带了 `name`**，不清的话别的主线的匹配列表里还是旧名字。

**这一条是摸代码时才发现的 —— 光看"改名"两个字完全想不到。**

### 11.5 为什么宁可全清缓存

见 3.3。核心：**漏一个就是"界面显示一条已经不存在的轨迹"**，而全清的代价只是 2 秒。

### 11.6 为什么回收站要用 fail-safe（导出失败就不删）

见 4.2。核心：**"尽力导出、失败也照删"的保险是假的** —— 用户以为有回收站，磁盘满了就静默没了。

### 11.7 为什么回收站不复用 `allowed-roots`

见 4.4。那个是**导入时的读白名单**，用途不同。混在一起会让两个安全策略互相牵制。
