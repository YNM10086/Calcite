## 一、背景与目标

### 1.1 为什么做这个

M2 的目标是「**算得出**」——从"能播放"升级到"能分析"。设项目总设计里 M2 规划了三件事：

| M2 功能 | 本文档 |
| --- | --- |
| **停留点识别**（空间距离 + 时间阈值） | ✅ 本文档 |
| 轨迹统计（总距离、均速、最高速、累计爬升） | ⏳ 下一个功能块 |
| 热点区域分析（`ST_SnapToGrid` 网格密度） | ⏳ 再下一个 |

**先做停留点的理由**：它是三个里唯一涉及**真正的算法设计**的（阈值、边界、脏数据），
做完之后另两个会顺理成章（统计复用轨迹遍历经验，热点复用"在地球上画东西"的经验）。

### 1.2 目标

从一条轨迹里找出「**在某个地方待了一阵子**」的片段，并且：

1. 结果能在地球上看到（每个停留点画一个范围圈）
2. 结果能在面板里逐条列出（起止时刻 / 时长 / 活动半径）
3. 点列表里的一条，地球飞过去
4. **不被真实数据的脏东西骗到**（见 1.3）

### 1.3 三个必须防住的真实陷阱（**全部来自实测数据**）

设计这个功能前，先用用户的真实数据做了探索，发现三个问题：

**① 信号中断会被当成"超长停留"**

实测轨迹 `20081115010133.plt`：设备在 `01:09:08` 停止记录，**2.3 小时后在原地恢复**。
如果用"首尾时间差 ≥ 阈值 且 半径 ≤ 阈值"判定，它会报出一个
**"停留了 2.3 小时"** 的荒谬结果（实测就是这样被误判的）。

**② 半径给太大，正常走路会被当成停留**

实测用户那 4 条校园步行记录：步行速度约 1.4 m/s。
若停留半径取 100 米，则"60 秒走 84 米"也算落在半径内 →
D=100m/T=60s 时，4 条记录冒出 **6~9 个**"停留点"——全是走的。

反过来 D=30m 时又几乎找不到（GPS 抖动导致点很散）。

**③ 基于速度的判据在这个数据上不可用**

用户站着不动时，逐点速度的 **5% 分位仍有 0.3~0.65 m/s**（GPS 抖动）。
"速度低于阈值持续 T 秒"这种判据会把"站着不动"判成"在移动"。

### 1.4 验收标准

- [ ] 已导入的 21 条 GeoLife 轨迹，用默认参数应识别出 **23 段**停留（实测值）
- [ ] `20081115010133` 里那个**假的 2.3 小时停留不再出现**（被 `G` 规则切断）
- [ ] 操场跑圈那条（2342 点、几乎全程匀速移动）返回 **0 段**停留
- [ ] 点数很少的轨迹（如 7 个点 / 2.4 分钟）返回**空列表**，不报错
- [ ] 地球上的圆圈画出来了，透明度/颜色能区分停留时长
- [ ] 面板列表点一条，地球飞过去
- [ ] 后端 JUnit 全绿（现有 46 项 + 新增）
- [ ] 面板在窗口拉矮时**两个列表各自滚动**，停留点区块不会被切掉

## 二、范围

### 2.1 做

| 项 | 说明 |
| --- | --- |
| 停留点识别算法 | 纯计算，可单测（不依赖 Spring / 数据库） |
| `GET /api/tracks/{id}/stay-points` | 一条新接口，**查询时现算** |
| 地球上的停留圆圈 | 半透明圆（范围）+ 颜色深浅（时长） |
| 面板的停留点列表 | 独立滚动区块，点一条飞过去 |
| 参数配置 | `application.yml` 里可调 |

### 2.2 不做（YAGNI）

| 不做 | 理由 |
| --- | --- |
| **把结果存进 `stay_point` 表** | 一条轨迹最多几千点，现算只要几毫秒；而且参数一改结果立刻跟着变，不用管缓存失效。**等要做"跨轨迹查询"（"这个区域被停留过几次"）时再入库才划算**——那是 M3 的事 |
| **在底部曲线上标出停留时段** | 用户明确选了布局 A（不加这个）。低成本、很容易后补 |
| 前端调参滑块 | 参数写死在配置里。**想要的话很容易加，演示时很好看** |
| 停留点命名 / 匹配 POI | "这里是什么地方"需要额外的 POI 数据源 |
| 跨轨迹的停留聚合 | 属于 M3 空间分析 |
| 停留点的语义分类（家 / 工作地） | 需要长期数据 + 聚类，远超 M2 |
| 停留点的编辑 / 删除 | 没有这个需求 |

## 三、算法设计（本文档的核心）

### 3.1 判据：滑动窗口 + 四条规则

```
输入：一条轨迹的点列表，已按时间升序（复用 TrackCleaner 的排序结果）
参数：D = 停留半径（米）  T = 最短停留时长（秒）  G = 最大采样间隔（秒）

i = 0
while i < n:
    j = i                                  # 窗口 = P[i..j]
    while j + 1 < n:
        [规则 4] 若 P[j+1].时间 - P[j].时间 > G  → 断开，停止扩窗
        [规则 2] 若 窗口 P[i..j+1] 内所有点到"窗口中心"的最大距离 × 2 > D → 停止扩窗
        j += 1
    [规则 3] 若 j > i 且 P[j].时间 - P[i].时间 >= T:
        记录一个停留点（中心 = 窗口中心，半径 = 窗口内最大距离）
        i = j + 1                          # 跳过整段，避免同一停留被拆成多个
    否则:
        i += 1
```

**四条规则的分工**：

| 规则 | 内容 | 防的是什么 |
| --- | --- | --- |
| 2 | 空间：窗口内所有点到中心 ≤ D/2 | 把"移动中"误判成停留 |
| 3 | 时间：窗口时长 ≥ T | 把"路过停一下"当成停留 |
| 4 | 采样：窗口内相邻点间隔 ≤ G | **信号中断被当成超长停留** |
| — | `i = j + 1` 跳段 | 同一个停留被拆成好几段 |

### 3.2 「窗口中心」怎么算

用**重心**（窗口内所有点经纬度的算术平均），而不是"第一个点"。

- 为什么不用第一个点：第一个点自身的 GPS 误差会污染整个判定
- 为什么可以用算术平均：在校园/城市这种几公里的尺度上，经纬度的算术平均与真实几何中心差别可忽略

`radiusM` = 窗口内所有点到该重心的**最大距离**（用现成的 `GeoUtils.haversineMeters`）。

### 3.3 默认参数与依据

| 参数 | 配置键 | 默认值 | 依据（实测） |
| --- | --- | --- | --- |
| `D` 停留直径 | `calcite.stay-point.radius-m` | **50 米** | D=100m 会把正常步行误判成停留（4 条记录冒 6~9 个假停留）；D=30m 又几乎找不到 |
| `T` 最短时长 | `calcite.stay-point.min-duration-s` | **300 秒** | 21 条 GeoLife 出 23 段——既不是 0 也不泛滥 |
| `G` 最大采样间隔 | `calcite.stay-point.max-gap-s` | **300 秒** | 那条 8217 秒的断档必须被切断 |

配置示例：

```yaml
calcite:
  stay-point:
    radius-m: 50
    min-duration-s: 300
    max-gap-s: 300
```

### 3.4 边界情况

| 情况 | 行为 |
| --- | --- |
| 点数 < 2 | 返回空列表（**不是报错**） |
| 没有找到任何停留 | 返回空列表（200，**不是 404**） |
| 轨迹不存在 | 404（沿用现有 `TrackController.detail` 的行为） |
| 配置值非法（≤ 0） | 启动时由 Spring 绑定失败（fail fast，不要静默用默认值） |
| 全部点在同一位置且时间够长 | 正常识别为一个停留（`radiusM` 会接近 0） |

### 3.5 算法放在哪

新增 `service/StayPointService.java`，**照 `TrackCleaner` 的模式**：

- 是 `@Component`，参数用 `@Value` 从配置注入
- 核心方法 `detect(List<RawPoint> points)` **是纯函数**——不碰数据库、不碰 Spring 上下文，可以直接单测
- 返回 `List<StayPoint>`（一个 record）

> 这样单测可以 `new StayPointService(50, 300, 300)` 直接构造，和 `TrackCleanerTest` 一样。

## 四、接口设计

### 4.1 请求

```
GET /api/tracks/{id}/stay-points
```

### 4.2 响应

```json
{
  "trackId": 5,
  "count": 3,
  "stays": [
    {
      "seqStart": 120,
      "seqEnd": 1450,
      "startTime": "2008-10-23T02:53:04Z",
      "endTime": "2008-10-23T03:16:05Z",
      "durationS": 1381,
      "center": { "lon": 116.318417, "lat": 39.984702 },
      "radiusM": 12.4,
      "pointCount": 1331
    }
  ]
}
```

**字段说明**：

| 字段 | 含义 |
| --- | --- |
| `seqStart` / `seqEnd` | 起止点在轨迹里的序号（前端可用来定位） |
| `startTime` / `endTime` | 起止时刻 |
| `durationS` | 停留时长（秒） |
| `center` | 停留中心（经纬度，已拆成独立数字，和 `TrackPointDto` 的风格一致） |
| `radiusM` | 活动半径（窗口内点到中心的最大距离，米） |
| `pointCount` | 这段里有多少个点 |

**为什么返回 `count` 和 `stays` 两层**：和 `TrackPage` 的 `{total, items}` 保持一致的风格；
前端要显示"停留点（3 处）"这个标题。

### 4.3 实现路径

```
TrackController.stayPoints(id)
  → TrackRepository.findById(id)          // 不存在则 404
  → TrackPointRepository.findByTrackIdOrderBySeqAsc(id)
  → 转成 List<RawPoint>（复用 import 功能里的 RawPoint 结构）
  → StayPointService.detect(points)
  → List<StayPoint> → List<StayPointDto>
```

**注意**：这里**不需要再跑一遍 `TrackCleaner`**——`track_point` 表里的数据在导入时已经排好序了
（`seq` 就是按时间顺序编的）。

## 六、前端设计

### 6.1 布局：面板下方独立区块（用户选定的 A 方案）

```
┌─ aside.panel（总高度限制在视口内）──────────┐
│ 标题 + 后端连通性                            │ 固定
│ [导入轨迹]                                   │ 固定
│ 轨迹列表  [来源▾] [条数▾]        共 25 条    │ 固定
│ ┌──────────────────────────────────────┐   │
│ │ 列表区（弹性高度 + 独立滚动）          │   │  ← 滚动不影响下面
│ └──────────────────────────────────────┘   │
│ 停留点（3 处）                               │ 固定
│ ┌──────────────────────────────────────┐   │
│ │ 停留区（独立滚动）                     │   │  ← 自己滚，也不会顶爆面板
│ └──────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
```

**关键 CSS 改动**：`.panel` 加 `max-height: calc(100vh - 32px)` 和 `display: flex; flex-direction: column`，
让两个列表区用 `flex: 1; min-height: 0; overflow-y: auto` 各自滚动。

> **为什么要这么改**：现在 `.track-list` 有自己的 260px 滚动盒，所以列表内容再多也不会顶开别人；
> **但 `.panel` 本身没有高度限制也没有滚动**——加上停留点区块后面板总高约 750px，
> 在矮窗口下停留点区块会被切掉且滚不到。这是用户提出的问题。

### 6.2 新建组件 `StayPointList.vue`

照 `TrackList.vue` 的规矩（**纯展示，不发请求**）：

| props | 说明 |

### 6.3 `CesiumGlobe.vue` 加停留圆圈图层

- 新增 prop `stayPoints`

## 九、风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 默认参数在别的数据上不合适 | 停留点太多或太少 | 参数是配置项，改配置重启即可；**并且写了真实数据回归测试钉住当前行为** |
| `ellipse` 实体在地球上的半径单位搞错 | 圆圈大小离谱 | 验收里加"圆面积与半径平方成正比"的检查；Cesium 的 `ellipse` 半径单位就是米 |
| 大量停留点的渲染性能 | 地图卡顿 | 按 8.4 观察；单条轨迹的停留数是个位到几十，量级很小 |
| 面板高度改动影响现有布局 | 轨迹列表或状态条错位 | 面板改动后跑一次现有的曲线/回放浏览器验收 |
