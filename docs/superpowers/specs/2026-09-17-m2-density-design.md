> 状态：待评审
> 前置：M2 第一阶段「停留点识别」、第二阶段「停留热点」均已完成
> 日期：2026-09-17

## 1. 目标与范围

### 要回答什么问题

设计文档 `2026-09-08-calcite-trajectory-analysis-design.md` 的**场景 3**：

> **早高峰哪些路段骑车的人最多？**

这就是**网格密度**：把地球切成固定边长的方格，数每个格子里有多少轨迹点 / 多少条轨迹，
用颜色深浅表示冷热 —— 一张**热力图**。

### 和上一阶段的分工（这个区分是理解本设计的第一把钥匙）

| | 停留热点（第二阶段） | **网格密度（本阶段）** |
|---|---|---|
| 输入 | **停留点**（264 个，由 Java 现算） | **原始轨迹点**（286,019 个） |
| 回答 | 哪些地方总有人**停下来** | 哪些**路段**总有人**经过** |
| 产物 | 一个个**热点圈**（离散的点） | 一张**方格热力图**（连续覆盖） |
| 本质 | 目的地分析 | **车流分析** |
| 算法 | 并查集聚类（Java 内存里） | 分桶聚合（**数据库里**） |
| 数据量 | 264 | 286,019 |
| 实测耗时 | 4.5 秒（超红线，见第 10 节） | **92 毫秒** |

> 💡 本阶段是**整个项目里第一个"把计算下推到数据库"的功能**。这不是炫技 ——
> 28.6 万个点搬到 Java 内存里聚合，和让数据库聚合完只返回 736 行，差了三个数量级的传输量。
> 设计文档选 PostGIS 的理由，在这里第一次真正兑现。

### 两个口径都保留（数据证明它们不同序）

| 口径 | 含义 | 特点 |
|---|---|---|
| `tracks` **轨迹条数**（默认） | 有几条**不同**的轨迹经过这个格子 | **不受"站着不动"污染**；直接对应"路段繁忙度" |
| `points` **点数** | 这个格子里累计有多少个采样点 | 站得越久越密；更接近"人在哪待着"（和上一阶段重叠） |

**实测证据**（0.001° 网格）：

| 排序口径 | Top1 格子 | 数值 |
|---|---|---|
| 按**点数** | `40.0135, 116.3065` | **12,562 点**，但只有 63 条轨迹 |
| 按**轨迹条数** | `39.9995, 116.3265` | 1,618 点，**140 条轨迹** |

两者 Top5 完全不同 —— 不是理论差异。

### 成功标准

1. 缩放到城市尺度，能在几十毫秒内拿到视野内的网格数据
2. 颜色能看出**路网结构**（而不是只有几个亮点）
3. 能按「早高峰」筛选，且筛选后**结论确实不同**
4. 拖动/缩放地图时**格子不跳动**，只在跨档时变一次
5. 切走密度档后，地球上的方格彻底消失（和另外两种圈互斥）

## 2. 真实数据现状（本设计的依据）

> 以下数字全部**实测**，脚本在 `.tmp/analyze-density.py`。数据已在 2026-09-17 扩充。

- **246 条轨迹 / 286,019 个点**（`track_point` 表 63 MB）
  - `geolife` 242 条 = **user 000（北京）171 条 + user 001（长三角）71 条**
  - `gpx` 3 条（用户自采，福建）+ `sample` 1 条
- ⚠️ **两个用户不在同一个城市**：GeoLife 数据跨 **467 公里 × 1008 公里**
  （经度 116.07~121.56，纬度 31.10~40.21）
- 用户自采的 3 条 GPX 在**福建**，与前两者相距 1000+ 公里

> 这一条直接导致"必须支持按视野裁剪"（见第 3 节）——
> 否则一次要返回跨 1000 公里的网格，每格只有 2 个像素，什么也看不清。

### 2.1 `ST_SnapToGrid` 的语义（实测确认）

```
ST_SnapToGrid(POINT(116.2964, 40.0114), 0.001) → POINT(116.296 40.011)
ST_SnapToGrid(POINT(116.2966, 40.0116), 0.001) → POINT(116.297 40.012)
```

**就近取整到 `size` 的整数倍** —— 也就是说**节点就是格子中心**，格子是以节点为中心、
边长 `size` 的方块。这个语义决定了前端怎么画（用中心点 ± cellSize/2）。

### 2.2 阶梯每一档在**全量数据**下的格子数（决定响应体积）

| 格边长 | 格子实际大小（纬度 40°） | 非空格子 | JSON 约 |
|---|---|---|---|
| 5° | 426 km × 553 km | 2 | 0.1 KB |
| 2° | 171 km × 221 km | 2 | 0.1 KB |
| 1° | 85 km × 111 km | 4 | 0.2 KB |
| 0.5° | 43 km × 55 km | 6 | 0.3 KB |
| 0.2° | 17 km × 22 km | 16 | 0.7 KB |
| 0.1° | 8.5 km × 11 km | 32 | 1.4 KB |
| 0.05 | 4.3 km × 5.5 km | 80 | 3.5 KB |
| 0.02 | 1.7 km × 2.2 km | 254 | 11 KB |
| 0.01 | 853 m × 1106 m | 598 | 26 KB |
| 0.005 | 426 m × 553 m | 1,359 | 60 KB |
| 0.002 | 171 m × 221 m | 3,867 | 170 KB |
| 0.001 | 85 m × 111 m | 8,329 | 366 KB |
| 0.0005 | 43 m × 55 m | 17,150 | 754 KB |
| 0.0002 | 17 m × 22 m | 41,437 | **1.8 MB** |
| 0.0001 | 8.5 m × 11 m | 75,631 | **3.3 MB** |

**结论 1**：一次性返回全量格子是不可行的（最细档 3.3 MB）。**必须按视野裁剪** ——
裁剪后北京城区 0.002° 只有 **736 个格子 / 约 33 KB**。

**结论 2 —— ⚠️ 阶梯的最粗档必须够粗，否则第一次用就报错。**

前端挑档的规则是"阶梯里 ≥ 视野宽度 ÷ 80 的最小那一档"，
所以**阶梯能覆盖的最大视野宽度 = 最粗档 × 80**。

- 如果最粗档只到 **0.05°**，能覆盖的最大视野就是 **4°**。
  而用户一打开地图就是**全球视野（360°）** → 挑档退回最粗档 →
  后端估算 `(360/0.05) × (180/0.05) = 2592 万` 个格子 → **超过 20000 上限，返回 400**。
  **也就是：点「密度」的第一眼就是报错。**
- 最粗档放到 **5°** 之后，能覆盖 400° > 360°，全球视野也走不到兜底分支：
  `ceil(360/5) × ceil(180/5) = 72 × 36 = 2592 ≤ 20000` ✓

> 这个坑在写实施计划时真的踩过一次：**测试是按宽阶梯写的，配置里却配了窄阶梯**，
> 两条测试互相矛盾（一条要求"宽视野也要 ≤ 80 格"，另一条钉住"过宽就退回最粗档"），
> 被执行任务的子代理抓了出来。现在有一条专门的测试覆盖到 360° 并同时守住格子上限。

### 2.4 时段筛选确实有区分度（实测）

| 筛选 | Top 格子（按轨迹条数） |
|---|---|
| 全天 | `116.322, 40.009`（11 条轨迹） |
| **只早高峰 7–9 点** | `116.297, 40.011`（3 条轨迹） |

**两个区域完全不同** —— 早高峰时段的点集中在西边，全天最忙的在东边。

各时段的数据量：早高峰（7-9）3,543 点 / 6 条轨迹；白天（10-16）4,375 点 / 12 条；晚间（17-22）1,857 点 / 10 条。

### 2.5 ⭐ 时区：必须显式写死（这是最容易错的坑）

- `track_point.recorded_at` 是 `timestamptz`，**存的是 UTC**
- 数据库会话时区是 **+08**，所以 `extract(hour FROM recorded_at)` 出来的碰巧是北京时间
- **但这依赖会话时区** —— 换台服务器、改了 `postgresql.conf`，同一个 `hourFrom=7` 会查出**完全不同**的结果

**所以 SQL 里必须写 `recorded_at AT TIME ZONE 'Asia/Shanghai'`**，并在测试里钉住。

> 顺带记录一个**验证过的、不是 bug 的结论**：`.plt` 文件里的时间是 **UTC**。
> 证据：把全部点按北京时间排小时分布，峰值在 **9-10 点**、活动集中在 7:00–23:00；
> 若 `.plt` 里是北京时间，这个人就在**凌晨 1-2 点**活动 —— 不可能。

## 3. 接口设计

### `GET /api/analysis/density`

| 参数 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `bbox` | ✅ | — | 当前视野：`西经,南纬,东经,北纬`（如 `116.26,39.86,116.42,40.04`） |
| `cellSize` | ✅ | — | 格边长（度）。**只接受阶梯里的 9 个值**，其它一律 400 |
| `metric` | | `tracks` | `tracks`（轨迹条数）或 `points`（点数） |
| `hourFrom` / `hourTo` | | 无 | 一天内的时段（**北京时间**，0–23，含两端） |
| `from` / `to` | | 无 | 日期范围（ISO，复用第二阶段的写法） |

**为什么 `cellSize` 由前端传、而不是后端按 bbox 算**：见第 9.2 节（档位阶梯的取舍）。

### 响应

```json
{
  "bbox": [116.26, 39.86, 116.42, 40.04],
  "cellSize": 0.002,
  "metric": "tracks",
  "scanned": { "cells": 736, "points": 68921, "maxTracks": 152 },
  "params": { "metric": "tracks", "hourFrom": null, "hourTo": null,
              "from": null, "to": null },
  "cells": [
    { "lon": 116.296, "lat": 40.012, "points": 912, "tracks": 3,  "value": 3 },
    { "lon": 116.322, "lat": 40.009, "points": 611, "tracks": 11, "value": 11 }
  ]
}
```

**三点说明**：

1. `lon` / `lat` 是**格子中心**（就是 `ST_SnapToGrid` 的节点），前端画 `cellSize` 见方的方格
2. 每个格子**同时带 `points` 和 `tracks`**，外加 `value`（按 `metric` 选出的那个）——
   这样**前端切口径不用重新请求**，而 `value` 让渲染逻辑保持简单
3. `scanned` 让前端能显示"736 个格子 / 68921 个点"，也能自证没有截断；
   其中 `maxTracks` 是**单格里最多的轨迹条数**（不是全库轨迹数 —— 名字带 `max` 以免误读）

### 错误处理

| 情况 | 返回 |
|---|---|
| `bbox` 缺失/格式错/西南角不小于东北角 | **400** + 说明 |
| `cellSize` 不在阶梯里 | **400** + 列出允许的 9 个值 |
| 估算格子数 > **20,000** | **400** + "请放大视野或换更粗的格子" |
| `hourFrom > hourTo` | **400** |
| 视野内没有数据 | **200** + `cells: []`（**不是错误**） |

**格子数估算公式**：`ceil((east-west)/cellSize) × ceil((north-south)/cellSize)`。
这是**上界**（不管有没有数据），所以它能防住"全球 bbox + 最细格子"这种攻击。

> **为什么不需要再加 `LIMIT` 或 `truncated` 字段**：估算值是**上界**，实际返回的格子数
> 一定 ≤ 它 ≤ 20,000。所以"返回被截断"这种情况**不可能发生** ——
> 加一个永远不会触发的字段只会让人误以为它有意义。
> 验证脚本里会**断言这一点**（实际格子数 ≤ 估算值）。

### `bbox` 的格式

`西经,南纬,东经,北纬`（GeoJSON / OGC 的常见顺序），例如 `116.26,39.86,116.42,40.04`。

⚠️ **和 `ST_MakeEnvelope(xmin, ymin, xmax, ymax)` 的顺序一致**（也是 西,南,东,北），
不要和"中心点 + 半径"的写法混淆。

## 4. 后端实现

### 4.1 核心 SQL

```sql
SELECT round(ST_X(geom) / :cell)::int              AS nx,
       round(ST_Y(geom) / :cell)::int              AS ny,
       count(*)                                    AS points,
       count(DISTINCT track_id)                    AS tracks
FROM track_point
WHERE geom && ST_MakeEnvelope(:west, :south, :east, :north, 4326)
  AND (:hourFrom IS NULL
       OR extract(hour FROM recorded_at AT TIME ZONE 'Asia/Shanghai')
          BETWEEN :hourFrom AND :hourTo)
  AND (:from IS NULL OR recorded_at >= :from)
  AND (:to   IS NULL OR recorded_at <= :to)
GROUP BY 1, 2
```

`nx * :cell` 就是格子中心的经度，`ny * :cell` 是中心纬度。

> **不加 `LIMIT`**：第 3 节的格子数上限是**上界**（用 bbox 算的，不管有没有数据），
> 所以实际返回的格子数不可能超过它 —— `LIMIT` 永远不会生效，加了只会让人误解。

### 4.2 ⭐ 为什么用 `round(ST_X/cell)` 而不是 `ST_SnapToGrid(...)`

**它们语义完全相同，但快 3.5 倍**（实测）：

| 写法 | 北京 0.002° 的格子数 | 全量格子数 | 耗时 | 备注 |
|---|---|---|---|---|
| `ST_SnapToGrid(geom, 0.002)` | 736 | 3,867 | **330 ms** | 要构造 geometry 并排序，**6.5 MB 临时文件落盘** |
| **`round(ST_X(geom)/0.002)::int`** | **736** | **3,867** | **92 ms** | 整数哈希聚合，不落盘 |

> **两种写法的格子集合逐个相同**（全量 3867 = 3867、北京 736 = 736）——
> 这不是"差不多"，是数学等价：`ST_SnapToGrid(p, s)` 就是"把每个坐标就近取整到 `s` 的整数倍"。
>
> **这个等价关系会写成自动化测试**（第 7 节），钉住"我们用整数运算替代了 PostGIS 函数"这件事。

### 4.3 空间索引：如实记录，不假装它被用上了

`track_point` 上确实有 `idx_track_point_st ON gist(geom, recorded_at)`，
但**当前数据量下优化器选择顺序扫描**（`EXPLAIN` 显示 `geom && ...` 落在 `Filter` 而不是 `Index Cond`）：

```
Parallel Seq Scan on track_point  (actual time=0.022..15.659 rows=68937.33)
  Filter: (geom && '...'::geometry)
```

强制走索引能到 187 ms（比全表 330 ms 快），但**整数写法（92 ms）比两者都快** ——
因为真正的瓶颈不是"扫多少行"，而是"排不排序"。

**结论**：当前不为了走索引而改写法；等数据量再上一个数量级时重新评估。
这条写进第 8 节的「已知限制」。

### 4.4 参数校验（全部在进入 SQL 之前）

| 校验 | 做法 |
|---|---|
| `bbox` 四个数、有限、西<东、南<北 | 解析后逐项检查，出错 **400** |
| `cellSize` ∈ 阶梯 | 用 `Double.compare` 逐个比对（**不能用 `==`**，浮点） |
| 估算格子数 ≤ 20000 | 见第 3 节公式 |
| `hourFrom`/`hourTo` ∈ [0,23] 且 `from ≤ to` | 范围检查 |
| `metric` ∈ {tracks, points} | 枚举检查 |

> `cellSize` 的比对**必须用 `Double.compare`**：`0.001` 这类十进制小数在二进制里不精确，
> 用 `==` 有可能比不中。这是浮点比较的经典坑，写进注释。

## 5. 前端设计

### 5.1 模式开关加第三档

`[停留点 | 热点 | 密度]` —— 沿用第二阶段那个开关，加一档。
**地球只画当前档的东西**（三档互斥，沿用第二阶段的 `:prop="mode === 'x' ? data : []"` 写法）。

### 5.2 相机事件驱动（这是"格子随缩放变"的落地）

```
camera.moveEnd  →  等 400ms（debounce）  →  取当前视野 bbox
                →  从阶梯挑一档 cellSize
                →  GET /api/analysis/density
                →  清空旧方格 → 画新方格
```

**挑档规则**：`cellSize = 阶梯里 ≥ (视野宽度 ÷ 80) 的最小那一档`

举例：

| 视野宽度 | 宽度÷80 | 选中的档 | 视野内格数 |
|---|---|---|---|
| 0.16°（北京城区） | 0.002 | **0.002** | 80 |
| 0.01°（街区） | 0.000125 | **0.0002** | 50 |
| 4°（大区域） | 0.05 | **0.05** | 80 |

**取 bbox 用 `viewer.camera.computeViewRectangle()`** —— 它可能返回 `undefined`
（视角包含极点或太空时）。**必须有退化处理**：返回 undefined 时就跳过本次请求，
不要把 `undefined` 传下去。

### 5.3 色阶：对数

```js
// max 取本次响应里的最大值；t ∈ [0,1] 后查色带
const t = Math.log1p(value) / Math.log1p(maxValue)
```

**⚠️ 关于"可比性"的如实说明**（这是设计评审时更正过的一个说法）：

- ✅ 对数的**映射是可预测的函数** —— 知道 max 就能反推数值。分位分档做不到（同值可能不同色）
- ❌ **但归一化用的仍是"本次响应的最大值"，所以跨视野不是绝对可比的**
- ❌ 而且**格边长随缩放变**，不同缩放下的计数值本来就不该直接比（格子大小差 10 倍）

**所以做法是**：颜色只在**同一视野内**可比；**图例上写出绝对刻度**，让绝对值可读：

```
[色条]  1 ── 3 ── 10 ── 30 ── 100 ── 300+
                                 最深 = 152 条轨迹
```

这条取舍写进第 8 节的「已知限制」，不含糊过去。

### 5.4 面板（密度档下显示什么）

1. **图例色条**（含绝对刻度）
2. **时段下拉**：全天 / 早高峰 7-9 / 白天 10-16 / 晚间 17-22
3. **口径切换**：按轨迹数 / 按点数
4. **统计行**：`736 个格子 · 68921 个点 · 152 条轨迹`
5. 三种状态：加载中 / 视野内无数据 / 请求失败

> 日期范围（`from`/`to`）**只在 URL 里支持，不做界面控件** —— 面板空间已经在第二阶段紧张过一次了。

### 5.5 渲染

每个格子一个 Cesium `rectangle` 实体，`coordinates = Rectangle.fromDegrees(lon-½cell, lat-½cell, lon+½cell, lat+½cell)`。

- 按档位规则，视野内格宽 50~80 格，**实际非空格子通常在 700~1500 个**
- 上限由后端 20,000 的硬保护兜底
- 清理沿用现有写法（实体数组 + 逐个 remove）

> **为什么先用 Entity 而不是 `GroundPrimitive`**：Entity 和现有代码风格一致、可读性好。
> 实测若发现相机移动后重绘明显卡顿，再换 `GroundPrimitive`（批量几何体）——
> 验收里会**测量重绘耗时**，不靠感觉。

### 5.6 组件

## 6. 参数与默认值

```yaml
calcite:
  density:
    # 格边长阶梯（度）。只允许这些值 —— 这样"换一档"是可复现的离散事件，
    # 而不是"随缩放连续变化"（后者会让网格每滚一下滚轮就整体错位）。
    #
    # ⚠️ 最粗那一档不能小于 4.5°：能覆盖的最大视野宽度 = 最粗档 × target-cells-across。
    # 用户一打开地图就是全球视野（360°），如果最粗档只到 0.05°（覆盖 4°），
    # 挑档会退回最粗档、算出 2592 万个格子、后端直接 400 —— 第一次用就报错。
    # 5° 能覆盖 400° > 360°，全球视野下 72 × 36 = 2592 个格子，安全。
    cell-ladder: [5, 2, 1, 0.5, 0.2, 0.1, 0.05, 0.02, 0.01, 0.005, 0.002, 0.001, 0.0005, 0.0002, 0.0001]
    # 视野内目标格数（挑档时用：cellSize = 阶梯里 ≥ 视野宽度/这个数 的最小档）
    target-cells-across: 80
    # 单次请求的格子数上限（超过直接 400，防止全地球 bbox + 最细格子）
    max-cells: 20000
    # 时区：库里存 UTC，但"早高峰"是人理解的北京时间，必须显式转换
    time-zone: Asia/Shanghai
```

⚠️ **`cell-ladder` 是 YAML 列表，必须用 `@ConfigurationProperties` 绑定，不能用 `@Value`。**

这是本项目**已经踩过的坑**（第一阶段导入功能）：
`@Value("${calcite.import.allowed-roots}") List<String>` **绑不上 YAML 列表**，
当时就是改成 `@ConfigurationProperties`（`config/ImportProperties`）才解决的。

### 6.1 类的划分：把"纯逻辑"和"碰数据库的"分开

**这是本设计里一个明确的架构决定**，因为它决定了测试怎么写。

| 类 | 职责 | 怎么测 |
|---|---|---|
| `service/DensityGrid.java`<br>**纯静态工具** | 解析校验 `bbox`、校验 `cellSize` ∈ 阶梯、挑档、算格子数上限、`nx/ny ↔ 经纬度` 换算、时区小时判定 | **Java 单测**（`new` 都不用，全是静态方法，不碰 Spring、不碰数据库） |
| `service/DensityService.java`<br>**Spring bean** | 编排：拿参数 → 调 `DensityGrid` 校验/换算 → 调 repository 查 SQL → 组装响应 | **Python 对拍**（需要真数据库） |

**为什么必须这样拆**：如果把校验逻辑写在 `DensityService` 里，那么为了测一个
"`cellSize` 非法要报错"，就得启动 Spring 上下文 + 连数据库 ——
**而现在的 72 个测试全都不需要数据库**，不能让第一个测试开这个头。

> 这个模式和项目里 `GeoUtils`（静态工具，被 `StayPointService` 和 `HotspotService` 复用）
> 是一致的。

## 9. 关键决策记录

### 9.1 为什么每格同时返回两个口径

数据证明「点数」和「轨迹条数」的 Top5 完全不同（第 1 节）。同时返回让前端能**秒切口径**，
而多出的体积很小（736 个格子 × 两个整数）。这和第二阶段"三个热度口径都返回"是同一条原则。

### 9.2 为什么格边长由前端传，而不是后端按 bbox 算

三种做法：

| 做法 | 问题 |
|---|---|
| 后端按"目标格数"实时算 `cellSize = 视野宽/80` | `cellSize` 变成任意小数 → **网格锚点随之改变** → 缩放时整个网格**整体错位、视觉上像在抖** |
| 前端固定一档（如 0.002°） | 放大到街区格子太粗、缩小到大区域格子太密 —— 和"随缩放变细"的需求矛盾 |
| ✅ **固定阶梯 + 前端挑档** | 只在**跨档那一瞬间**变一次，其余时候**拖动地图格子纹丝不动**；且可复现、能写测试 |

`ST_SnapToGrid` 的网格锚定在绝对坐标（`size` 的整数倍）上，所以**只要 `cellSize` 不变，
平移地图时格子绝对不动**。这正是"离散档位"比"连续变化"好的根本原因。

### 9.3 为什么用 `round(ST_X/cell)` 而不是 `ST_SnapToGrid`

见 4.2：语义逐个相同，但快 3.5 倍、不落盘。**并用自动化测试钉住这个等价关系。**

### 9.4 为什么时区必须显式写 `AT TIME ZONE 'Asia/Shanghai'`

见 2.5：库里存 UTC、会话时区是 +08。不显式写的话，换台机器 `hourFrom=7` 就查出别的结果。
**这类"依赖运行环境默认值"的代码是最容易在部署时炸的。**

### 9.5 为什么 `mvn test` 不引入数据库依赖

见 7.1。SQL 正确性改用 Python 对拍来验证 —— 这也是本项目一贯的**交叉验证**做法
（第二阶段那个对拍脚本抓出过我写的 haversine 错了一层 `sqrt`）。

## 10. 附带任务

### 10.1 停留热点接口的性能修复（用户已选方案 A）

**问题**：导入数据后，`GET /api/analysis/hotspots` 从 0.9 秒涨到 **4.5 秒**，
超过第二阶段自己定下的 2 秒红线。

**原因**：该接口把**全部 28.6 万个点搬进 Java 内存**逐条算停留点。数据量线性放大。

**方案 A（已选定）：按 `trackId` 缓存算好的停留点**

### 缓存放哪儿（这一条很重要，不要放错地方）

**❌ 不要放进 `HotspotService`。** 它在第二阶段被特意设计成**无状态**的
（"参数走方法参数、类本身无状态、测试里直接 `new` 就能跑"），
而且它有 **14 个单元测试**建立在"无状态"这个前提上。往里塞一个 `Map` 会破坏这个设计。

**✅ 新增一个独立组件 `service/StayPointCache.java`**：

```java
@Component
public class StayPointCache {

    /**
     * trackId → 该轨迹的停留点。
     *
     * <p><b>为什么这个缓存永远不会失效</b>：停留点是
     * {@code trackId → 该轨迹的全部点} 的纯函数，而轨迹一旦导入就<b>不可变</b>
     * （系统里没有"编辑轨迹""删除轨迹""覆盖同名轨迹"这些功能）。
     * 所以同一个 trackId 的结果恒定。
     *
     * <p><b>⚠️ 将来如果加了这些功能，这里必须清理</b>：删除轨迹、重新导入并覆盖、
     * 或者停留点参数变成「每条轨迹可不同」。当前都不存在。
     */
    private final Map<Long, List<StayPoint>> cache = new ConcurrentHashMap<>();

    public List<StayPoint> get(Long trackId, Supplier<List<StayPoint>> compute) {
        return cache.computeIfAbsent(trackId, k -> compute.get());
    }

    /** 仅供测试与将来的"重新导入"功能使用 */
    public void invalidate(Long trackId) { cache.remove(trackId); }
}
```

`ConcurrentHashMap.computeIfAbsent` 天然保证并发下同一个 trackId 只算一次。

### 效果与代价

- **收益**：第一次请求仍要 ~4.5 秒（要算 246 条），**之后每次只算新导入的轨迹** ——
  切到热点档接近瞬时
- **代价**：内存里存 264 个 `StayPoint`（几百字节）；**进程重启后缓存清空**（可接受）
- **不做**：不引入过期/淘汰策略（不需要，因为不会失效）；不改数据库表结构
- **`HotspotService` 一行都不改** —— 它的 14 个测试和"无状态"设计原样保留
