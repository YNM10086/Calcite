## 0. 一句话

> **把所有轨迹的「停留点」汇总起来，把挨得近的合并成「一个地点」，并统计这个地点被访问的强度。**

第一阶段回答的是「**这一条**轨迹的人在哪停过」；
这一阶段回答的是「**哪些地方**总有人停」—— 它必须跨轨迹，所以是新的一层。

## 1. ⭐ 先回答你的疑问：你的数据为什么没有热点

你打开前端后说：「我自己提供的数据没有能形成热点的地方，所以这次没有显示是吧」。

**这句话对了一半，我把两半分开说清楚**：

| 你的判断 | 对不对 | 实际情况 |
|---|---|---|
| 你的数据形不成热点 | ✅ **对** | 你的 3 条 GPX（资料一 / 资料二 / sample）**停留点都是 0 个** |
| 所以这次没显示 | ❌ **不对** | 热点**显示了 3 个**，只是**全部来自 GeoLife 的数据** |

![图 1 · 为什么你在热点里看不到自己的数据](docs/learning/figs/fig-hot-1-why.png)

### 真正让你"没看懂"的原因：两地相距 1665 公里

| | 你的数据 | GeoLife |
|---|---|---|
| 大致位置 | **福建（25.03°N, 117.02°E）** | **北京五道口一带（40.00°N, 116.32°E）** |
| 轨迹条数 / 点数 | 3 条 / 1821 点 | 21 条 / 11899 点 |
| **停留点数** | **0** | **10** |
| 热点数 | 0（没有停留点，自然没有热点） | **3** |

**两个原因叠在一起**：

1. **你的轨迹里根本没有"停留"** —— 那几条是跑步/走路轨迹，全程在动。
   而停留点的判定要求「**在 50 米范围内待够 5 分钟**」，跑步途中没有这种时刻
2. **你的数据在福建，热点在北京，相距 1665 公里** —— 一切到「热点」档，
   相机就飞到了北京的包围盒，**你的轨迹线直接被甩出屏幕**。
   所以屏幕上"看起来什么都没有"，其实是"你的人在画面外"

> 💡 **所以不是 bug，是你这批数据本来就不该有热点。** 这其实是件好事 ——
> 说明算法没有把"跑步经过的地方"误判成"停留"（那才是真出问题）。

### 如果你想让热点里出现自己的数据

去一个地方（比如教室、食堂、家门口）**站定 5 分钟以上**再走，导出 GPX 重新导入，
那条轨迹就会产生停留点。**同一个地方去两次以上**，才会聚成一个热点
（去一次只是孤立点，不算热点）。

## 2. 前端怎么用

![图 2 · 前端怎么用](docs/learning/figs/fig-hot-2-howto.png)

就三步：

1. **点面板上的「热点」档** —— 在「轨迹列表」下面那个两档开关里
2. **地球自动飞过去** —— 飞到能装下所有热点的位置
   （这一步有个坑：面板会盖住画面左边，所以取景时会**刻意往右让**，
   否则西边那个热点会藏在面板底下 —— 这是实测踩出来的）
3. **点列表里任意一条** → 相机单独飞过去

**两个视觉通道各表达一件事**：

| 看到什么 | 含义 |
|---|---|
| 圆点**越大** | 被停留的次数越多 |
| 颜色**越红** | 来过的**轨迹条数**越多（≈ 越多人来过） |
| 颜色**偏黄** | 只有 1 条轨迹，也就是**同一个人常来** |

> 分成两个通道是有必要的：你数据里有个热点是「4 次 / 3 条轨迹」，
> 另一个是「2 次 / 1 条轨迹」。只用"大小"表达的话，这两个说不清区别。

右上角还有个**排序下拉**（按轨迹数 / 按次数 / 按时长）。
⚠️ 说实话：**你当前这 3 个热点在三个口径下顺序是一样的**，所以切了看不出变化 ——
不是坏了，是数据恰好同序。

## 3. 热点是怎么算出来的（就 5 步）

```
① 把「所有轨迹」的停留点收集起来，每个都记住它属于哪条轨迹
② 两两算球面距离
③ 距离 ≤ 200 米的，连一条边
④ 连成一片的（连通分量）就算【一个热点】
⑤ 里面点数 < 2 的，判为【孤立点】，不算热点
```

**两个参数**（都在 `backend/src/main/resources/application.yml` 里）：

| 参数 | 默认 | 为什么是这个值 |
|---|---|---|
| `radius-m` | **200** | 实测 45 对距离排序后，**118.3 米之后直接跳到 231.5 米**，中间空了 113 米。所以 **119~231 米之间取任意值，结果完全一样** —— 200 落在空档正中，不敏感 |
| `min-visits` | **2** | 只去过一次的地方不该叫"热点" |

## 4. 真实结果（这就是你在前端看到的那 3 个）

| # | 中心坐标 | 停留次数 | 轨迹条数 | 累计时长 | 真实散布 |
|---|---|---|---|---|---|
| 1 | 40.011572, 116.296853 | **4** | **3** | 1730 秒 | **9.4 米** |
| 2 | 40.008948, 116.321793 | 3 | 3 | 1228 秒 | 58.1 米 |
| 3 | 40.006719, 116.296562 | 2 | **1** | 650 秒 | 59.1 米 |

> 扫了 25 条轨迹 / 10 个停留点 → **3 个热点 + 1 个孤立点**（第 4 个只去过一次，被排除了）

**热点① 值得单独说**：同一个人在**三周内**（10-28、11-04、11-11）去了同一个地方 4 次，
而且这 4 次**彼此相距不到 10 米**。这是最典型意义上的"常去地点" —— 算法把它找出来了。

**热点③ 是另一个类型**：`停留次数 = 2` 但 `轨迹条数 = 1` —— **同一个人去了两次**。
这也是为什么热度要留三个口径，下面单独讲。

## 5. 为什么"热度"要留三个口径

同一批数据，用不同口径排出来的顺序**可能不一样**：

| 口径 | 回答的问题 | 在你数据上的表现 |
|---|---|---|
| `visitCount` 停留次数 | 这里被停留过几次 | 热点③（2 次）比孤立点（1 次）热 |
| `trackCount` 轨迹条数 | 有**几个不同的人**来过 | 热点③ 和孤立点**一样冷**（都只有 1 条轨迹） |
| `totalDurationS` 累计时长 | 一共待了多久 | 热点① 最久（1730 秒） |

> **"同一个人来两次" 和 "两个人各来一次"，是不是一回事？**
> 取决于你要回答什么问题 —— 所以三个都留着，而且后端一次全返回，前端能切换排序。
>
> 另外顺带一提：这个项目里"排名"的排序规则是**五级**
> （轨迹数 → 次数 → 时长 → 纬度 → 经度），后两级是为了让结果**完全确定**、
> 与输入顺序无关 —— 只写三级时，三项全平局的两个热点顺序会漂，测试就没法钉死。

## 6. 已知限制（你能感知到的）

| 限制 | 表现 | 为什么先不修 |
|---|---|---|
| **热点可能横跨几百米** | A 挨着 B、B 挨着 C，即使 A 和 C 相距 300 米也会合成**一个**热点 | 这是"单链聚类"的定义（不是 bug），已写成测试钉住。要消除得换算法 |
| **两两比较是 O(n²)** | 停留点上万时会明显变慢 | 现在只有 10 个点；缓解办法（按经纬度分桶）等真慢了再上 |
| 停留点**不入库** | 每次请求都重新算一遍 | 现在 25 条轨迹只要几百毫秒。**触发入库的条件**：轨迹超过 500 条，或接口超过 2 秒 |
| 时间窗没有前端控件 | 后端支持 `?from=` / `?to=`，前端没做界面 | 用不上，等需要再加 |
| 热点不告诉你"这是哪儿" | 只给坐标，不说"这是北京西站" | 属于另一个功能（POI 匹配） |
| 排序下拉看不出效果 | 见第 2 节末尾 | 当前数据三个口径同序 |

## 7. 术语表

| 术语 | 大白话 |
|---|---|
| **停留点** | 第一阶段算出来的"这个人在这儿待过一会儿" |
| **热点** | 把**跨轨迹**、挨得近的若干停留点合并成的一个"地点" |
| **孤立点** | 只被停留过 1 次的地方 —— 不算热点，不出现在结果里 |
| **聚类半径** | 多近算"同一个地点"，默认 200 米 |
| **轨迹条数** | 有几条**不同**的轨迹来过（不是停留次数） |
| **真实散布** | 这个热点里所有停留点离中心最远有多远（**不是画出来的圈的大小**） |
| **链式效应** | 单链聚类的传递性：隔着两跳也算一堆 |

## 8. 想自己调参数时

改 `backend/src/main/resources/application.yml` 里的 `calcite.hotspot`，**重启后端**即可：

```yaml
calcite:
  hotspot:
    radius-m: 200
    min-visits: 2
```

也可以**临时用 URL 参数覆盖**（不用重启，方便试）：

```powershell
# 默认：3 个热点
Invoke-RestMethod "http://localhost:8080/api/analysis/hotspots" | Select-Object -Expand hotspots | Format-Table rank, visitCount, trackCount

# 半径放大到 300 米：热点会连成一片，只剩 2 个
(Invoke-RestMethod "http://localhost:8080/api/analysis/hotspots?radiusM=300").hotspots.Count

# 只让去过 3 次以上的算热点
(Invoke-RestMethod "http://localhost:8080/api/analysis/hotspots?minVisits=3").hotspots.Count

# 非法参数会返回 400（不是 500）
try { Invoke-RestMethod "http://localhost:8080/api/analysis/hotspots?radiusM=-1" }
catch { "HTTP " + [int]$_.Exception.Response.StatusCode }
```
