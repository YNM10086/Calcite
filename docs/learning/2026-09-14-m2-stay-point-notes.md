## 0. 先用一句话说清楚这一段做了什么

> **给它一条轨迹，它还给你一份「这人中间在哪几个地方停过、各停了多久」的清单，
> 并且在地球上把每个停留点画成一个半透明的橙色圆圈。**

前端长这样：左边面板上半截是轨迹列表，下半截是停留点列表；点一条停留点，
地球上的圆圈会转正对着你，底部曲线不动（这是你选的布局 A）。

真实数据跑出来的效果：21 条 GeoLife 轨迹 → **一共 10 个停留点**。

## 2. 为什么这件事比想象的难

![图 1 · 停留点是什么，以及为什么它比想象的难](docs/learning/figs/fig-s1-what.png)

停留点的定义听起来很简单：**"这个人在这块地方待了一会儿没走"**。

难就难在：**GPS 不是尺子。** 它每次报给你的坐标都有误差，而且误差不小。

### 拦路虎 ①：GPS 会飘，所以"没动"不等于"坐标不变"

人站着不动的时候，手机每秒报的坐标能差出**十几米**。

我实测过：**即使站着不动，逐点速度的第 5 百分位仍然有 0.3 ~ 0.65 米/秒。**

这个数字是致命的 —— 它意味着"速度小于 0.5 米/秒 就算停留"这条路**直接废掉**，
因为站着不动的速度就已经在这个范围里了，走路也差不多，两者根本分不开。

> 💡 **这一条改变了整个算法方向。**
> 如果速度可用，一行代码就能判断；正因为速度不可用，才必须改用**空间 + 时间**两个维度一起判断。

### 拦路虎 ②：信号会断，所以"时间差大"不等于"待得久"

进地铁、手机没电、高楼遮挡丢星……都会让中间几百秒**一个点都没有**。

真实数据里就有一条轨迹断了 **8217 秒（2.3 小时）**，断开前后人还在同一个位置。
算法看到的是"首尾时间差了 2.3 小时 + 位置没怎么变"，于是非常合理地判成"停留了 2.3 小时"。

**但这个结论是错的** —— 中间那 2.3 小时根本没有数据，人可能早就走了又回来了。

### 拦路虎 ③：半径给大了，走路也会被算成停留

假设我们把"活动半径"设成 100 米。那么"60 秒走了 84 米"这件事，
首尾两点都在 100 米圈里，就会被判成停留 —— 可人明明在走路。

反过来把半径收到 30 米，真实的停留又几乎全被漏掉（GPS 飘移本身就有十几米）。

**所以半径必须小（我们取 50 米），而且必须配一个"最短时长"一起用。**

> 📌 **记住这三个拦路虎，后面四条规则就是一条一条对应着它们来的。**

## 3. 算法的整体思路：一个只会往右滑的窗口

![图 2 · 算法主流程](docs/learning/figs/fig-s2-flow.png)

想通了拦路虎 ①，思路就出来了：

> **既然没法判断"某一点是不是停着"，那就换一个问法 ——
> 「从第 i 个点开始，最多能连续圈进多少个点，而且这些点还都挤在一小块地方？」**

这就是**滑动窗口**。用一个很生活化的比喻：

> 想象你用手指按住地图上的一个点，然后**尽量往右把后面的点一个个揽进来**。
> 每揽一个，就检查一下：**"现在揽住的这一堆，还都挤在 25 米以内吗？"**
> 一旦揽不动了（再揽就散开了），就停下来看看：**"我揽住的这一把，时间跨度够长吗？"**
> 够长 → 记一个停留点；不够长 → 说明这里只是路过，把最左边那个点扔掉，从下一个点重新来。

用一个**游标 i 和 j** 表示这个窗口：

```
               i             j
   点:  ● ● ● ● ● ● ● ● ● ● ● ● ● ●
       └────窗口────┘
```

- `i` 是窗口左端（起点）
- `j` 是窗口右端（当前揽到哪了）
- 程序不断尝试把 `j` 往右推；推不动了就结算 `[i..j]` 这一段

### 为什么这个思路能绕开"GPS 飘移"

因为**它不要求任何单个点精确**，只要求"这一堆点在空间上足够集中、在时间上足够长"。

GPS 飘移是**随机的**：它会让点在这一小片区域里乱跳，但**不会让它们整体飘到 50 米外去**。
所以"一堆点都挤在 25 米内"这件事，对飘移是**天然免疫**的。

> 🎯 **这是整个算法最重要的设计思想，也是我希望你记住的一条通用经验：**
> 当单个数据不可靠时，不要想办法去"修"单个数据，而是**换一个对噪声不敏感的判据**。

## 4. 四条规则，一条一条拆

![图 3 · 四条规则](docs/learning/figs/fig-s3-rules.png)

算法核心只有 30 行，但里面藏了四条规则。**少任何一条都会出错**，所以逐条讲。

代码在 `backend/src/main/java/com/calcite/service/StayPointService.java`。

### 规则 1 · 空间：窗口内所有点到重心的距离 ≤ 25 米

**管什么**：挡住"其实在走路"（拦路虎 ③）。

**怎么算**：先把窗口里所有点的**重心**（平均经纬度）算出来，然后找**离重心最远**的那个点，
量一下它有多远。如果这个距离的两倍还超过 50 米，就说明这一堆点散得太开了。

```java
// StayPointService.java 第 73 行
if (radiusOf(points, i, j + 1) * 2 > radiusM) {
    break;   // 再揽就散开了，窗口到此为止
}
```

> ⚠️ **一个命名上的坑，要专门说一下：**
> 参数叫 `radius-m`（半径），但它实际起作用的方式是**直径上限**。
> 代码判断的是 `2 × 最远距离 ≤ 50`，也就是**任意两点的距离都不会超过 50 米**。
> 所以配置里写 50，实际的活动半径上限是 **25 米**。
> 这个"名不副实"是我自己的疏忽，将来如果重构，应该改名成 `diameter-m`。

**为什么用重心而不是"第一个点"**：如果拿窗口第一个点当圆心，那这个点自己的 GPS 误差会
把整个判断带偏。用重心相当于让所有点"投票"，对单个点的误差更不敏感。

**去掉它会怎样**：整条轨迹会被当成一个巨大的停留点 —— 因为只要不断往右揽，
`i` 是固定的，`[i..n]` 这一段在空间上迟早会散开，但如果不判断空间，
它就会一路揽到轨迹最后一个点。

### 规则 2 · 时长：窗口首尾时刻相差 ≥ 300 秒

**管什么**：挡住"路过"（拦路虎 ③的另一半）。

```java
// StayPointService.java 第 79-81 行
long span = Duration.between(points.get(i).recordedAt(),
                             points.get(j).recordedAt()).toSeconds();
if (j > i && span >= minDurationS) { ... }
```

有两个细节要注意：

- **是用"时刻相减"，不是"点数 × 采样间隔"**。因为真实数据的采样间隔根本不是均匀的 ——
  GeoLife 有的地方 5 秒一个点，有的地方 1 分钟一个点。用点数乘间隔会算错。
- **`j > i` 这个判断不能省**。如果窗口里只有一个点（`j == i`），首尾时刻相减等于 0，
  虽然 0 < 300 不会被误判，但显式写出来更清楚，也防住了"只有一个点"这种边界。

**去掉它会怎样**：在路口等一个 20 秒的红灯，就会报出一个停留点。

### 规则 3 · 断档：窗口内相邻两点间隔 ≤ 300 秒 ⭐

**管什么**：挡住"信号中断"（拦路虎 ②）。

```java
// StayPointService.java 第 67-71 行
long gap = Duration.between(points.get(j).recordedAt(),
                            points.get(j + 1).recordedAt()).toSeconds();
if (gap > maxGapS) {
    break;   // 中间没数据，窗口在这里就断了
}
```

**这是四条规则里最容易被漏掉、也是最有故事的一条**，下一节单独讲。

### 规则 4 · 跳段：找到一个停留点后，`i` 直接跳到 `j + 1`

**管什么**：挡住"同一段停留被报好几次"。

```java
// StayPointService.java 第 83 行
out.add(build(points, i, j));
i = j + 1;      // ← 跳过整段
```

对比一下另一种写法 `i = i + 1`：那样的话，从 `i+1` 开始又会把后面几乎同一批点再揽一遍，
于是**一次真实的停留会输出几十个严重重叠的结果**。

**注意这里是"跳过整段"，不是"跳过一部分"** —— 因为我们相信窗口已经尽可能往右撑过了，
`j+1` 这个点之所以没被揽进来，就是因为揽进来会破坏规则。

## 5. 规则 3 的来历：真实数据里的一次 2.3 小时断档 ⭐

![图 4 · 规则 3 的来历](docs/learning/figs/fig-s4-gap.png)

**这一节是整份笔记里我最想让你看的。** 因为它完整展示了"算法是怎么被真实数据教出来的"。

### 事情经过

我最初写的探索脚本里，**只有规则 1、2、4，没有规则 3**。
在合成的小数据上它跑得很好，于是我很自信地拿真实数据去跑 ——

```
21 条轨迹的停留段数：23
```

当时我觉得"嗯，21 条轨迹找出 23 个停留点，挺合理"。

**但我觉得应该交叉验证一下**，于是另外写了一份独立的 Python 脚本重算。数字对不上。
于是一条一条轨迹去对，最后锁定了 `20081115010133`：

```
01:09:08  最后一个点
          ←—— 中间 8217 秒（2.3 小时）一个点都没有 ——→
03:46:05  恢复，位置和断开前几乎一样
```

### 算法当时"看到"的是

- 首尾时刻差了 8217 秒，远 ≥ 300 秒 → **"时长够了"** ✅
- 空间上前前后后都在同一处 → **"半径也没超"** ✅

**结论：这个人在这里停留了 2.3 小时。** —— 一个看起来无懈可击、实际完全错误的结论。

### 加上规则 3 之后

算法看到那 8217 秒里**有一个断档**，窗口在这里就断了。断成两段之后，
每一段的时间跨度都不到 300 秒 → **什么也不报**。

而这正是正确答案：这条轨迹**应该输出 0 个停留点**。

### 修正后的影响

| | 21 条轨迹的停留段数 |
|---|---|
| 漏掉规则 3 | **23 段**（虚高 2.3 倍） |
| 加上规则 3 | **10 段**（正确答案） |

> 🎯 **我想让你记住的两件事：**
>
> **① 算法一定要拿真实数据验一遍。** 合成数据是自己造的，自己造的数据里不会有自己没想到的坑。
> 23 这个数字当时"看起来合理"，但它错了。
>
> **② 交叉验证很值。** 如果我只有一份实现，它输出 23 我就信 23 了。
> 正是因为另写了一份独立脚本去对，才逼出了这个 bug。
> 这也是为什么后面我会专门做"真实数据指纹测试"（第 10 节）。

## 6. 拿真实数据完整跑一遍

![图 5 · 真实数据跑一遍](docs/learning/figs/fig-s5-real.png)

用测试夹具 `backend/src/test/resources/sample-real.plt`（908 个点的真实 GeoLife 轨迹）。

**算法的输出**：

```
第 519 ~ 589 号点 · 时长 306 秒 · 半径 24.22 米 · 共 71 个点
```

图 5 右边那条曲线，就是**窗口一点点长大的过程**：横轴是"窗口里现在有几个点"，
纵轴是"这一堆点里最远的那个离重心多远"。

可以看到曲线一路往上爬，中间有几个明显的台阶（揽进了一个偏远的点），
**最后停在 24.22 米 —— 再撑一格就会超过 25 米的上限，所以算法在这里收手了。**

左边那张散点图是把这 71 个点画在平面上（换算成以重心为原点的米）。
橙色虚线圈是 25 米的规则上限，绿色实线圈是实际算出来的 24.22 米 —— 两条线几乎重合，
说明这个窗口**是"撑到极限"才停的**。

### 为什么这段特别适合当"指纹测试"

看这两个数字：

- 时长 **306 秒**，离 300 秒的门槛只差 **6 秒**
- 半径 **24.22 米**，离 25 米的上限只差 **0.78 米**

**两个阈值都贴得这么近。** 这意味着算法但凡被改错一点点（改个比较符号、
把 `<=` 写成 `<`、重心算错一个除法的位置），这个测试**立刻就会变红**。

这就是所谓的**指纹测试**：不测"功能对不对"，而是给算法在当前参数下的行为**拍一张快照**，
一旦行为漂移就报警。它比普通的"输入 A 期望输出 B"更敏感，因为它挑的是**临界样本**。

## 7. 两个"反直觉但正确"的行为

写测试的过程中，有两个现象一开始让我以为代码写错了，查了半天才发现**是算法本身的固有特性**。
我把它们单独列出来，因为将来你自己看结果时一定会再遇到。

### 现象 A：停留窗口会"多吃"接近的那几秒

假设真实情况是"从 10:00:00 站到 10:10:00"（600 秒）。
但 09:59:50 那个点，人**已经开始往这里走了**，它离最终停留中心可能只有 20 米 —— **在 25 米以内**。

于是算法从 `09:59:50` 就开始起窗口，一路揽到 `10:09:50`（再往后就超半径了）。

**结果报出来的是 579 秒，而不是 600 秒。** 而且起点比真实停留**早了 10 秒**。

> **这是"贪心地往左吃"的必然代价**：算法只看"在不在圈里"，不区分
> "这个点是人已经站定了"还是"这个点是人正走过来、恰好路过圈内"。

**要不要修？** 我选择**不修**，理由是：

- 修的话需要引入"速度权重"或者"回溯修正"，复杂度上一个台阶，收益只有几秒
- 停留时长本来就是**估计值**，±10 秒对"他在这儿待了 5 分钟"这个结论毫无影响
- 更重要的是：**这个行为是确定的、可预测的**，我把它写成测试钉住了

> 💡 **一条工程经验**：不是所有"不完美"都要修。
> 只要它是**确定的**、**影响可量化的**、并且**被你写进测试钉住了**，
> 那就记录下来、接受它，把精力留给真正的问题。

### 现象 B：起点提前的代价，是能容纳的点变少

接着上面的例子：窗口从 `09:59:50` 开始，意味着它**多吃了一个离中心较远的点**。
这个点会把"重心"往它那边拽一点，从而**让半径提前撞到 25 米上限** ——
于是窗口能揽进来的点**变少了**，结束时刻也提前了。

**起点提前 → 重心偏移 → 半径提前超标 → 结束也提前。**

这是个连锁反应，不是 bug。合成用例里 600 秒的停留被报成 579 秒，就是这么来的。

## 8. 一个停留点从数据库走到屏幕上

![图 6 · 数据流](docs/learning/figs/fig-s6-dataflow.png)

沿着这条线走一遍，就知道每个文件为什么存在、要改东西该动哪个。

| 步骤 | 文件 | 干什么 |
|---|---|---|
| ① 前端发请求 | `frontend/src/App.vue` | `GET /api/tracks/5/stay-points` |
| ② 接请求、捞数据 | `backend/.../web/TrackController.java` | 从数据库取出这条轨迹的所有点，拆成 `(lat, lon, 时刻)` |
| ③ **核心算法** | `backend/.../service/StayPointService.java` | 滑动窗口 + 四条规则 ⭐ |
| ④ 转成 JSON | `backend/.../web/dto/StayPointDto.java` | 时刻 / 时长 / 中心点 / 半径 / 点数 |
| ⑤ 前端收下来 | `frontend/src/App.vue` | 存进 `stays`，分发给列表和地球 |
| ⑥ 画出来 | `StayPointList.vue` + `CesiumGlobe.vue` | 面板逐条列出 + 地球上画半透明橙圈 |

### 几个设计上的选择，值得单独说

**① 算法类完全不碰数据库**

`StayPointService` 的签名是：

```java
public List<StayPoint> detect(List<RawPoint> points)
```

**输入是一个普通的 Java 列表，输出也是一个普通的 Java 列表，中间不碰数据库、不碰 Spring。**

这么设计的好处很实在：**测试里直接 `new StayPointService(50, 300, 300)` 就能跑**，
不需要启动 Spring、不需要连数据库。12 个测试跑完只要几秒钟。

> 💡 **通用经验**：把"纯计算"和"IO"分开。纯计算的类最好连框架都不要沾，
> 这样它既好测、又好复用（将来做热点分析时可以拿它当零件）。

**② 结果现算，不存数据库**

`stay_point` 这张表**建好了但一直是空的**。

理由：一条轨迹几千个点，现算只要**几毫秒**；而且参数一改结果立刻跟着变，
不用管"缓存失效"这种麻烦事（改了参数忘了重算，是这类系统最常见的 bug 来源）。

**什么时候该入库？** 等 M3 要做"**跨轨迹查询**"的时候 —— 比如"这个商场被多少条轨迹停留过"，
那时候没法一条条现算，才值得入库。

> 💡 **通用经验**：**不要为了"以后可能用得上"提前做优化。**
> 现在不入库，代价是几毫秒；提前入库，代价是缓存一致性的复杂度。

**③ `StayPoint` 用的是 Java 的 `record`**

```java
public record StayPoint(
    int seqStart, int seqEnd,
    OffsetDateTime startTime, OffsetDateTime endTime,
    int durationS,
    double centerLon, double centerLat, double radiusM,
    int pointCount) {}
```

`record` 是 Java 16 之后的新写法：**一行就把"一个只用来装数据的类"写完了** ——
自动生成构造器、`getter`、`equals`、`hashCode`、`toString`。

而且它**天生不可变**（所有字段都是 final），这意味着算法内部可以放心地把
`StayPoint` 对象传来传去，不用担心谁把它改了。**"算法输出"这种东西就该是不可变的。**

## 9. 参数在哪调，调了会怎样

三个参数都在 `backend/src/main/resources/application.yml`：

```yaml
calcite:
  stay-point:
    radius-m: 50          # 停留直径（米）—— 注意是直径，实际半径上限是它的一半
    min-duration-s: 300   # 最短停留时长（秒）
    max-gap-s: 300        # 最大采样间隔（秒），超过就认为窗口断了
```

**改完重启后端即可，Java 代码一行都不用动。**

各参数的影响（这些数字是实测出来的，不是估的）：

| 参数 | 调小会怎样 | 调大会怎样 |
|---|---|---|
| `radius-m: 50` | 调到 30 → 真实停留几乎全漏掉（GPS 飘移本身就有十几米） | 调到 100 → 正常走路被判成停留，21 条轨迹里会冒出 6~9 个假停留 |
| `min-duration-s: 300` | 调到 60 → 等个红灯都算停留 | 调到 900 → 只留下"待了 15 分钟以上"的，短停留全丢 |
| `max-gap-s: 300` | 调到 60 → GeoLife 有些地方采样间隔本来就有 1 分钟，会被大量误断 | 调到 3600 → 2.3 小时那种断档又会漏网 |

> ⚠️ **参数的默认值是有依据的**：`300 秒` 对应"人停留 5 分钟以上才算一次有意义的停留"
> （这是轨迹挖掘文献里的常用阈值）；`50 米` 是在"别漏掉真实停留"和"别把走路算进去"之间
> 试出来的平衡点。

## 10. 怎么证明它是对的：三层防线，一共 119 项检查

算法这种东西，"我觉得对"是不算数的。这一段一共建了**三层防线**：

### 第一层 · 合成用例（后端 12 个单元测试）

`backend/src/test/java/com/calcite/service/StayPointServiceTest.java`

一共有 12 个，覆盖的思路是这样的：

| 测什么 | 测试名 |
|---|---|
| 基本行为 | 匀速移动的轨迹_没有任何停留 |
| | 中间停了一段_正好识别出_1_个停留 |
| | 停了两次_识别出_2_个停留 |
| 断档（规则 3） | 采样断档_不会被拼成超长停留 |
| | 采样断档_两边各自够长时各算一段 |
| **边界**（最容易错的地方） | 时长刚好达到阈值_应被识别 |
| | 时长差一秒_不该被识别 |
| | 半径刚好在阈值内_应被识别 |
| | 半径超出阈值_不该被识别 |
| 极端输入 | 点数不足两个_返回空列表而不是报错 |
| | 全部点在同一位置_识别为一段停留且半径接近零 |
| **真实数据指纹** | 真实文件_默认参数下正好_1_段停留 |

> 💡 **看这个表的结构**：8 个测试里有 4 个是**边界测试**（"刚好达到" / "差一秒" / "刚好在内" / "超出"）。
> 边界是 bug 最喜欢藏的地方 —— 把 `>=` 写成 `>` 这种错误，只有边界测试才抓得到。

### 第二层 · 真实数据指纹

最后那个 `真实文件_默认参数下正好_1_段停留`，就是第 6 节讲的那段。它一口气断言了 6 个精确值：

```java
assertEquals(1, stays.size());                              // 正好 1 段
assertEquals(306, s.durationS());                           // 时长 306 秒
assertEquals(24.2, s.radiusM(), 0.2);                       // 半径 24.2 米（±0.2）
assertEquals(71, s.pointCount());                           // 71 个点
assertEquals(OffsetDateTime.parse("2008-10-23T09:50:00Z"), s.startTime());
assertEquals(OffsetDateTime.parse("2008-10-23T09:55:06Z"), s.endTime());
```

**这 6 个数字是先写 Python 独立算出来的，再抄进 Java 测试的** ——
所以它不是"把程序现在的输出抄下来当期望值"（那样等于没测），
而是"用另一套独立实现算出的答案"。

另外，第 7 节讲的那两个反直觉行为，也被一条测试专门钉住了
（`中间停了一段_正好识别出_1_个停留`）：它断言 `seqStart` 落在 `[45, 60]`，
并且 `durationS == 579`。**将来谁改了扩窗策略，这条会立刻红。**

- 停留点列表真的渲染出来了

### ⚠️ 顺带说一下浏览器验收抓到的一个真 bug

面板的 `z-index` 原来是 **10**，底部曲线是 **15**。面板变高之后**伸进了曲线区域**，
于是被曲线盖住，鼠标点上去 Playwright 报 `svg intercepts pointer events`。

**修法**：面板 `z-index` 改 **20**，`max-height` 改成 `calc(100vh - 220px)`（留出曲线的高度）。

> 这个 bug **单测和构建都抓不到** —— 只有真的在浏览器里点一下才会暴露。
> 这就是为什么"三层防线"里必须有端到端这一层。

## 11. 以后往哪加

![图 7 · 以后想改这个功能，分别动哪里](docs/learning/figs/fig-s7-extend.png)

这是整份笔记里最实用的一张表 —— **左边是"我想……"，右边是"动这个文件"**：

| 我想…… | 动哪里 | 怎么动 |
|---|---|---|
| **调参数** | `application.yml` | `calcite.stay-point.*` 三行，重启后端即可 |
| **加一条新规则**（比如限制最高速度） | `StayPointService.java` 的 `detect()` | 在扩窗口的判断里加一个 `if ... break`；新参数照抄 `@Value` 的写法 |
| **换一套算法**（比如 DBSCAN 聚类） | 只换 `StayPointService` 的内部实现 | `detect(List<RawPoint>)` 的签名不变，Controller / 前端 / 测试全都不用动 |
| **把结果存进数据库** | 新加 SQL + `StayPointRepository` + 改 `TrackController` | `stay_point` 表已经建好了、一直空着；等 M3 要跨轨迹查询时再做 |
| **做"热点区域"**（哪些地方总被停留） | 新建一个 `HotspotService` | 拿所有轨迹的停留点当输入做空间聚类；复用现成的 `GeoUtils` 距离函数 |
| **在曲线上标出停留时段（色带）** | `frontend/src/lib/chart.js` + `SpeedChart.vue` | 这阶段你选了不做（布局 A）；要做时给图加一层矩形即可 |

> 🎯 **注意"换一套算法"那一行的价值**：因为 `detect()` 的**输入输出类型是稳定的**，
> 所以整个功能被切成了一块"可替换的零件"。上面三行（Controller / 前端 / 测试）
> 都只跟 `detect()` 的**签名**打交道，不关心里面怎么实现。
>
> **这就是"接口稳定"带来的好处** —— 也是为什么当初要把算法单独抽成一个类，
> 而不是把逻辑塞在 Controller 里。

### M2 后面还有两件事

按设计文档，M2 一共三块：**停留点 → 热点区域 → 轨迹相似度**。
停留点这块（第一阶段）今天做完了，剩下两块：

- **热点区域**：把**所有轨迹**的停留点汇总起来做空间聚类，找出"哪些地方经常有人停留"
- **轨迹相似度**：判断两条轨迹是不是走的同一条路

它们都**建立在今天的停留点之上** —— 这就是为什么第一阶段要先把算法做扎实。

## 13. 术语表（只列这份笔记用到的）

| 术语 | 大白话 |
|---|---|
| **轨迹（track）** | 一个人一段时间里所有 GPS 点的集合 |
| **点（track_point）** | 某时刻的一个 GPS 坐标 + 时间戳 |
| **停留点（stay point）** | 从轨迹里找出来的"这人在这块地方待了一会儿" |
| **滑动窗口** | 用两个游标 `i`、`j` 圈出的一段连续的点，`j` 不断往右推 |
| **重心（centroid）** | 一堆点经纬度的平均值，可以理解成"这堆点的中心" |
| **活动半径** | 窗口里离重心最远的那个点，到重心的距离 |
| **断档（gap）** | 相邻两个点之间隔了太久，中间没数据 |
| **阈值（threshold）** | 用来做判断的临界值，比如 300 秒、25 米 |
| **边界测试** | 专门测"刚好等于临界值"和"刚好差一点"的测试 |
| **指纹测试** | 给算法当前行为拍一张快照，行为一变就报警 |
| **幂等（idempotent）** | 同一个操作做一遍和做十遍，结果一样（重复导入同一文件不会产生重复数据） |
