## 1. 一句话

把原来那个「导入轨迹」按钮，升级成了一个完整的**数据管理视图**：
**添加 / 替换 / 改名 / 删除** 都能在界面上做了。

---

## 2. 你现在能做什么

原来面板上只有一个「导入轨迹」按钮，点开是一张上传表单。现在点它，**整个面板切换成管理视图**
（不是从按钮下方展开一个小框）：

```
← 返回          数据管理
＋ 添加数据
资料一  gpx  456 点  715 米      ✎ 🗑
资料二  gpx  623 点  949 米      ✎ 🗑
```

| 操作 | 行为 |
|---|---|
| ✎ 改名 | **行内编辑**（不弹窗，直接在表格那一行改） |
| 🗑 删除 | 弹确认框，**文案里写出这条轨迹的真实点数**，并告诉你文件会被放到哪个回收站目录 |
| ＋ 添加数据 | 原来的上传表单搬进来了；**撞名时弹三选一**：「替换它 / 新增为另一条 / 取消」 |

---

## 3. ⭐ 这个功能真正的主题：兑现 M2 留下的两处欠账

`StayPointCache` 和 `SimilarityCache` 的 javadoc 里一直写着同一句话：

> 将来加了**删除轨迹 / 重新导入覆盖同名轨迹**，**必须调用 `invalidate` 清理**。

在 M2 那会儿，这两句话是"将来时"——**根本没有任何代码路径能走到它**。这次把它们接上了。
用四条关键测试证明（全部实测通过）：

| 测试 | 之前 | 之后 |
|---|---|---|
| 删掉相似度第一名 → 主线 20 的 `compared` | 197 | **196** |
| 改名 → 别的主线的匹配列表 | 旧名字 | **新名字** |
| 删除前回收站文件 | — | **真的落盘**（点数一致、带每个点的时间） |
| 新增导入 → `compared` | 196 | **197** |

> **第一条最关键。** 缓存要是没清，拿到的还是旧结果，`compared` 会**一点不变**——
> 接口看着"正常返回 200"，其实在撒谎。

---

## 4. 回收站（一个自己加的保险）

删除**不是真删**，而是先把这条轨迹导出成 GeoJSON、落到回收站目录，再动数据库：

```
D:\Calcite-note\backups\deleted\20260921-203953_20081203151206_279点.geojson
```

文件名里带着**时间戳 + 幂等键 + 点数**，一眼能认出是哪一条、几个点。

**fail-safe 是实测过的**：把回收站目录改成写不进去之后，`DELETE` 返回 **500，并且那条轨迹原样保留**——
不是"删了但没备份"。

---

## 5. 四个关键设计决定

1. **删除前先导出，导出失败就不删** —— "尽力导出、失败也照删"式的保险是**假的**：
   真出事的那一刻，备份恰好不存在。
2. **同名上传返回 409，让用户决定** —— 同名是**意图问题**，系统猜不准你是想覆盖还是想再存一条；
   而自动替换**不可逆**。
3. **替换保持 `trackId` 不变**（原地更新，不删不插）—— 前端已经选中的那条轨迹不会突然指向空。
4. **改名也必须清相似度缓存** —— 因为 `SimilarityMatch` 里带了 `name` 字段。
   这一条是**摸代码时才发现的**，只盯着"改名"两个字完全想不到。

## 6. ⚠️ 过程中的两个真实教训

**① `maxTracks` 是"最多处理几个文件"，不是"最多补几条"。**

为了补回被删掉的那一条轨迹，传了 `maxTracks: 400`，结果把**其它用户 399 个从未导入过的文件**
也扫进来导了 —— 数据从 **245 条涨到 645 条**。已用 SQL 删干净，数据完全恢复。

教训：批量导入的参数要**按"文件数"理解**，补数据之前先算清会扫到哪些文件。

**② 跑验收前必须确认后端跑的是当前源码。**

对拍脚本第一次跑就是红的，看着像"新增导入没清缓存"这种重大发现；实际是
**JVM 启动时间早于编译时间**——跑的是旧代码。

判别方法：比对 **`JVM 启动时间`** 和 **`ImportService.class` 的编译时间**，谁早谁可疑。

## 7. 性能：一个容易被误读的现象

实测数字（这是用户这次亲自问的："改完之后相似度是不是变慢了？"）：

| | 冷（第一次查某条主线） | 热（再查同一条） |
|---|---|---|
| 相似度 | **1433 ms** | **10 ~ 26 ms** |
| 热点 | 7.9 s | **3.2 s** |
| 密度（无缓存） | 307 ms | 307 ms |

**如果感觉"改完数据之后相似度变慢了"，那不是变慢，是缓存开始真的失效了：**

| | 这个功能之前 | 现在 |
|---|---|---|
| `SimilarityCache.invalidateAll()` | **从来没被调用过**（方法写了，但没人用） | **删除 / 改名 / 替换 / 新增 都会清** |
| 体感 | 查过一次之后**一直**是 10 毫秒 | 每次改完数据，下一次查是冷的（约 1.4 秒） |

**这不是变慢，是"缓存开始真的失效了"** —— 而这正是这个功能的目的：不失效的话，
界面会显示一条**已经被你删掉**的轨迹。

设计里的取舍写得很直白：**宁可全清，不要漏清**。漏一个的后果是显示错误数据；
全清的代价只是下次点相似度多等一秒多。

顺带指出一个真问题：**热点接口热态 3.2 秒**（M2 时记的是 1.9 秒）。
它每次都要读 **28.6 万个点**，**这部分不受缓存影响**，是 M2 就记在账上的欠账。
